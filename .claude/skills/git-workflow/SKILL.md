# Git Workflow — Potok

**Флоу тут не описаний.** Гілки, комміти, гейт, merge, деплой і заборони —
у `CLAUDE.md`. Ця сторінка колись дублювала його цілком і за один рольаут
розійшлася з ним у чотирьох місцях (стверджувала, що CI немає, що `main` без
branch-protection, що lint/typecheck-кроків не існує, і називала кількість
тестів числом). Друга копія правил завжди розходиться з першою — тому тут
лишилось тільки те, чого в `CLAUDE.md` немає.

Адреси репозиторіїв — `git remote -v`. Склад гейта — `.gitea/workflows/gate.yml`
і `Makefile`. Симптоми падінь — `.claude/skills/troubleshooting.md`.

---

## 1. Single writer і гігієна дерева

- **Один писар на робоче дерево.** В один момент лише одна сесія пише,
  комітить і мержить у `~/Developer/Potok`. Паралель — тільки через
  `git worktree add ../Potok-<slug> -b <branch>`.
- Ніякої branch-surgery (checkout / reset / `branch -f` / rebase / чужий stash),
  поки інша сесія пише в те саме дерево. HEAD «стрибнув» під тобою або
  з'явились чужі незакомічені зміни → **STOP + REPORT**, не «чинити» наосліп.
- Стеші не плодити; чужі стеші та WIP не чіпати — тільки повідомити.
- Фонові процеси не плодити. Прибирати за собою: scratchpad, тимчасові
  контейнери й volume'и, тестові записи.
- **Дерево чисте на кінець кожної задачі**; стан фіксувати у звіті
  (HEAD / гілка / чи запушено в Gitea).
- Локальний dev-стек не плутати з продом на сервері. `make verify` піднімає
  його на зсунутих портах саме тому, що 8080 і 5432 на машині зазвичай уже
  зайняті іншим проєктом.

---

## 2. Економія merge-ів

Дорогий ресурс — **merge-подія**: кожен merge у `main` тягне за собою збірку
docker-образу на двоядерному сервері. Економити треба merge-и, а не прогони.

- Пов'язані готові зміни батчити в одну гілку.
- Кілька готових гілок у черзі — запропонувати власнику згрупувати.
- Локальний `make verify` безкоштовний, ганяти скільки треба.

Гейт на маці теж не безкоштовний за часом, але за нього платить не прод.

---

## 3. Формат звіту

| Задача | Гілка | Змінено | Гейт |
| ------ | ----- | ------- | ---- |
| M\<N\> — slug | feat/m\<N\>-slug | файли/області | зелений, прогін #\<N\> |

+ один рядок outcome: **змержено в `main`** (`<sha>`), деплой пішов
(результат — у журналі деплоїв на сервері).

Тіло squash-комміта:

```markdown
## Summary
<1–3 речення, що зроблено>

## Changes
- <файл або область> — <що змінилось>

## Tests
- <додані/оновлені тести; backward-compat тест>

## Notes
<відхилення, рішення, міграції Flyway V<N>, зміни дефолтів>
```

Без co-author і «generated with» футерів.

---

## 4. Відкати

- **Прод.** Провал збірки або health-check відкочується сам — прод лишається
  на попередній версії. Деталі механізму — у `server-infra`.
- **Код.** `git revert <sha>` → PR → зелений гейт → merge → новий деплой.
  `git reset --hard` на опублікованих коммітах — **ні**, і force-push у `main`
  теж ні: це операція власника.
- **Схема БД.** Flyway вперед-онлі. Відкат схеми — нова міграція `V<N+1>`,
  а не редагування вже застосованої.

---

## 5. Коли деплой упав

1. Спершу матч симптому в `.claude/skills/troubleshooting.md`.
2. Не збіглося — розібратись і **додати запис**.
3. Чинити **наступним коммітом** через PR. Ніколи не force-push'ем.

CC деплой руками не тригерить і доступу до нього не має — лише знає механізм
і читає результат.
